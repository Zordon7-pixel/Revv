### Findings

**MED-1 — Genuinely-absent categories render `$0.00` instead of being omitted (spec "omit null" gap + test blind spot).**
Both backend paths (`normalizeEstimateTotals` and `parseEstimateTotalsFromPdfText`, plus `bmsParser`) emit **explicit `null`** for every unfound field — never `undefined`. In the frontend, `Number(null) === 0` is finite, so `hasNumber(null)` returns `true` and `formatUSD(null)` returns `"$0.00"`. Consequence: a real estimate missing a category (e.g. no mechanical labor, no paint) renders `Mechanical Labor: 0 hrs @ $0.00/hr = $0.00`, `Parts: $0.00`, etc., rather than omitting the row as the spec requires ("only render rows whose value is non-null"). The two negative tests use `{}` (fields `undefined`, correctly omitted) and so **do not exercise the real backend shape** (explicit nulls), masking this. Not CRITICAL/HIGH: no NaN/`$null`/crash, the headline + populated rows are correct, the reference estimate (all categories present) displays perfectly, and `$0.00` is factually defensible. Suggested tightening: treat `null`/`undefined` as absent in `hasNumber`/`laborSummary` (e.g. `value != null && Number.isFinite(Number(value))`) and add a test feeding explicit-null category fields.

**LOW-1 — `laborSummary` early-return `if (!hasNumber(cost))` never trips for `null` cost** (same `Number(null)=0` root cause as MED-1); folds into the MED-1 fix.

**LOW-2 — Test coverage gap:** negative-case tests should include an `estimate_totals` with explicit `null` category fields to match production data, not just `{}`.
